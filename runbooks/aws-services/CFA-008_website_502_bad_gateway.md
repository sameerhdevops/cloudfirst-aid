# Runbook: Website Returns HTTP 502 Bad Gateway (CFA-008)

## 1. Problem
Website visitors and synthetic monitoring probes receive:
```text
HTTP/1.1 502 Bad Gateway
```
The reverse proxy (Nginx or AWS Application Load Balancer) is reachable and responding, but it cannot proxy the request to the upstream application.

## 2. What the Engineer Sees
From client side:
```text
$ curl -I https://app.example.com
HTTP/2 502
date: Wed, 23 Oct 2026 04:22:15 GMT
content-type: text/html
content-length: 157
server: nginx/1.22.1
```
Checking Nginx error log on the proxy server (`/var/log/nginx/error.log`):
```text
2026/10/23 04:22:15 [error] 18412#18412: *1041 connect() failed (111: Connection refused) while connecting to upstream, client: 198.51.100.22, server: app.example.com, request: "GET / HTTP/1.1", upstream: "http://127.0.0.1:8000/", host: "app.example.com"
```
Or in an ALB access log:
```text
elb_status_code=502 target_status_code=-
```

## 3. Before Changing Anything
1. **Understand what 502 means:** An HTTP 502 error is generated by an **edge proxy** (Nginx, HAProxy, or ALB), NOT by the client and NOT by the origin web framework. It means: "I tried to forward your HTTP request to the upstream backend, but the backend either refused the TCP connection, reset the connection, or returned malformed data."
2. **Examine the `target_status_code` in ALB logs or `upstream` in Nginx logs:**
   - If `111: Connection refused`: The backend process is dead, crashed, or not listening on that port.
   - If `110: Connection timed out`: A firewall/Security Group is dropping the proxy-to-backend packets.
   - If `upstream sent invalid header`: Backend application threw an unhandled exception before sending HTTP status headers.

## 4. Investigation Sequence

### Step 1: Check Reverse Proxy Error Logs (Read-only Diagnostic)
- **Command:**
  ```bash
  sudo tail -n 30 /var/log/nginx/error.log
  ```
- **What to look for:**
  - `connect() failed (111: Connection refused)` -> Proceed to Step 2.
  - `connect() failed (110: Connection timed out)` -> Proceed to Step 3.
  - `upstream prematurely closed connection` -> Proceed to Step 4.

### Step 2: Check If Backend Process is Alive (Read-only Diagnostic - Connection Refused)
- **Command:**
  ```bash
  sudo systemctl status gunicorn.service  # or node / uwsgi / php-fpm
  ```
- **Interpretation:**
  - If `Active: failed` or `inactive (dead)`: Backend process has crashed.
  - Check recent service crash logs:
    ```bash
    sudo journalctl -u gunicorn.service -n 50 --no-pager
    ```

### Step 3: Check Sockets and Port Bindings (Read-only Diagnostic)
- **Command:**
  ```bash
  sudo ss -tlnp
  ```
- **What to look for:**
  - Is the upstream port (e.g. `8000` or `3000`) listed in the `Local Address:Port` column?
  - Does the listening IP match the Nginx `proxy_pass` directive? (e.g., if Nginx proxies to `127.0.0.1:8000`, backend must not be bound only to a specific internal IP like `10.0.1.50:8000`).

### Step 4: Test Upstream Backend Directly via Local Loopback (Read-only Diagnostic)
- **Command:**
  ```bash
  curl -Iv http://127.0.0.1:8000/
  ```
- **Interpretation:**
  - If `Failed to connect`: Backend is not running or listening.
  - If `Empty reply from server`: Backend process crashed as soon as it accepted the request.
  - If `HTTP/1.1 200 OK`: Backend works locally; check proxy configuration or permissions.

## 5. Possible Causes & Likelihood
| Cause | Likelihood | Distinguishing Evidence |
|---|---|---|
| Upstream application daemon crashed | **High** | `systemctl status` shows failed; `ss -tlnp` shows port closed. |
| Unix domain socket permissions incorrect | **Medium** | Error log shows `connect() to unix:/tmp/app.sock failed (13: Permission denied)`. |
| Port mismatch between Nginx config and application | **Medium** | App listening on 3000, Nginx `proxy_pass` points to 8000. |
| Target Security Group blocking ALB (for ALB architecture) | **High** | ALB logs show `Target.Timeout` or `target_status_code=-`. |

## 6. Remediation

### If Application Process Crashed (Local System Change):
Restart the backend service and inspect crash log for root cause (e.g. unhandled syntax error, database connection failure):
```bash
sudo systemctl restart gunicorn.service
```

### If Unix Domain Socket Permission Error (Local System Change):
Ensure the Nginx worker user (`nginx` or `www-data`) has read/write permissions on the socket:
```bash
sudo chown www-data:www-data /run/app.sock
sudo chmod 660 /run/app.sock
```

### If ALB Architecture (AWS Infrastructure Change):
Ensure target instance Security Group authorizes traffic on the target port from the ALB Security Group:
```bash
aws ec2 authorize-security-group-ingress \
  --group-id sg-backend-target \
  --protocol tcp \
  --port 8000 \
  --source-group sg-alb-frontend
```

## 7. Verification
Run curl through the proxy:
```bash
curl -Iv https://app.example.com
```
Expected output:
```text
HTTP/2 200
content-type: text/html; charset=utf-8
...
```

## 8. Prevention & Best Practices
1. **Process Supervision:** Always run application backends under systemd or supervisor with `Restart=always` and `RestartSec=3s`.
2. **Health Checks:** Configure Application Load Balancers with target health checks so traffic is automatically shifted away from crashing instances before users experience 502s.

## 9. Interview Discussion Points
- **Q: What is the primary architectural difference between an HTTP 500 and an HTTP 502?**
  - *Answer:* An **HTTP 500 Internal Server Error** is generated by the origin application itself (e.g., Python, Node.js, Java) when unhandled code exceptions occur. An **HTTP 502 Bad Gateway** is generated by an intermediary reverse proxy or load balancer because it could not communicate with or receive a valid HTTP response from the upstream application server.
- **Q: In ALB access logs, what does a hyphen `-` in the `target_status_code` column mean?**
  - *Answer:* A hyphen `-` indicates that the request was never forwarded to or answered by a target backend. The ALB itself terminated the connection and generated the error response (e.g. 502 or 504) because targets were unhealthy or network connections timed out.
